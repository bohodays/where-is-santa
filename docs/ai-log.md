### 경로 계산 규칙
- **잘한 것:** 산타 위치를 "시각 → 위치" 순수 함수로 정의하자는 구조를 바로 제안했다. 데모 모드와 테스트가 같은 원리로 풀렸다.
- **틀린 것:** 기획서 초안에서 AI가 도착 규칙을 "현지 시계 자정 + 시간대 안에서 경도 보정"으로 적었다. 이 방식은 중국처럼 넓은 시간대에서 경로가 앞뒤로 튄다.

### 첫 설치 검증과 lock 파일·CI 정리
- **잘한 것:** 처음으로 실제 npm 설치 환경에서 typecheck, lint, test(15개), build를 돌렸고 모두 통과했다. 고칠 코드는 없었다. Windows에서 만든 lock 파일이 Linux CI에서도 동작하는지 미리 확인했다. Linux용 바이너리 항목이 있는지 보고, CI의 npm 10으로 `npm ci --dry-run`을 돌렸고, `npm ci`로 새로 설치한 뒤 네 검사를 다시 돌렸다.
- **틀린 것:** 검사는 모두 통과했지만 `npm install`과 `npm audit`에서 취약점 15건(moderate 9, high 3, critical 3)이 나왔다. `next@15.2.4`는 설치할 때 보안 취약점 경고도 뜬다. 검사 통과만으로는 의존성이 안전한지 알 수 없다.
- **고친 방법:** lock 파일을 커밋하고 CI를 `npm ci`와 `cache: npm`으로 바꿨다(`chore/lockfile-npm-ci` 브랜치). 취약점은 아직 고치지 않았다. 버전을 올리는 일은 별도 변경으로 나눠 판단받기로 했다. 바꾼 CI는 PR #1에서 통과했고, 머지는 사람이 직접 했다.

### 의존성 보안 업데이트
- **잘한 것:** 버전을 올린 뒤 audit을 다시 돌려 안 풀린 취약점을 찾았다. `npm install`이 의존성 충돌(ERESOLVE)로 막혔을 때 `--force` 없이 원인을 찾아 해결했다. critical은 3건에서 0건, 전체는 15건에서 8건으로 줄었다.
- **틀린 것:** AI가 audit 안내만 보고 `vitest`는 2.1.9로 해결되고 현재 메이저 안에서 끝난다고 말했다. 실제로는 critical이 그대로 남아서 5.1.0까지 메이저 업그레이드가 필요했다. `next` 15.5.29도 `postcss` 8.4.31을 고정해서 쓰므로 high가 남았다.
- **고친 방법:** `next`와 `eslint-config-next`는 15.5.29, `vitest`는 5.1.0, `@types/node`는 22.20.5로 올렸다. `vitest` 5에 맞춰 `engines.node`도 22.12 이상으로 올렸다. 앞으로 "이 버전으로 해결된다"는 말은 설치 후 audit 결과로 확인하고 한다. 남은 8건은 `postcss`(Next 15 내부와 직접 의존성)와 린트 도구 쪽이다. Next 16 전환은 기술 스택 규칙과 관련되어 사람이 판단한다.

### postcss 취약점 overrides 처리
- **잘한 것:** 빌드 전 CSS를 기준선으로 저장해 두고 변경 후 결과와 비교했다. 운영 의존성의 audit은 2건에서 0건, 전체는 8건에서 6건(moderate)으로 줄었고, CSS는 바이트 단위로 같았다.
- **틀린 것:** 첫 시도에서 `overrides`를 넣었는데도 lock 파일에 옛 `postcss` 8.4.31이 남아 실제로는 적용되지 않았다. `npm ci`와 네 검사가 모두 통과했고 CSS도 같아서, 그 결과만 봤다면 해결됐다고 오해할 뻔했다.
- **고친 방법:** audit과 `npm ls`에 남은 8.4.31을 보고 문제를 찾았다. lock 파일 전체를 다시 만들지 않고 `next`만 다시 설치해 적용했고, `next`가 실제로 불러오는 버전이 8.5.32인지 확인했다. Next 16으로 올릴 때 이 `overrides`는 지운다.

### 시간대 경계 사례 테스트
- **잘한 것:** 30분·45분 시간대, 넓은 단일 시간대, 날짜변경선 양쪽을 테스트 24개로 고정했다. 기대값은 코드 결과를 복사하지 않고 공식으로 직접 계산했다. 일부러 넣은 버그 12개 중 기존 테스트는 5개를 잡았고, 새 테스트는 12개를 모두 잡았다. 이번 테스트로 찾은 코드 버그는 없었다.
- **틀린 것:** 기존 "밤에 도착" 테스트는 시각만 보고 날짜는 보지 않아서 하루 밀린 오류를 놓칠 수 있었다. 날짜변경선 비행도 위치가 유효한 값인지만 확인해서, 지구 반대쪽으로 도는 버그를 잡지 못했다. 처음 작성한 새 테스트도 시간대의 분을 버리는 보정 버그 1개를 놓쳤다.
- **고친 방법:** 현지 도착을 날짜까지 비교하고, 모든 구간에서 산타가 최단 경로 위에 있는지 별도 공식으로 확인했다. 놓친 버그는 일부러 버그 넣기에서 발견해 분 단위 보정 테스트를 추가했다. 이 테스트는 실제 도시에 없는 가상 조합으로 규칙만 고정한다.

### 지도 성능 시험과 MapLibre 확정
- **잘한 것:** 시험 화면에 측정 패널(LCP, 지도 준비 시간, FPS, 긴 프레임)과 결과 복사 버튼을 넣어, 폰에서 잰 값을 그대로 받아 비교했다. 카카오톡 인앱 브라우저에서도 지도가 동작하는 것을 확인했다. 저사양 흉내 측정에서는 로딩 시간(느린 4G 첫 방문 8.2초)이 핵심 문제라는 것을 찾았다.
- **틀린 것:** 지도 영역의 높이가 0이라 지도가 안 보였는데, 콘솔 오류가 없고 측정값도 정상이라 숫자만으로는 알 수 없었다. 저사양 흉내 측정의 FPS가 60으로 나온 것도 그대로 믿으면 안 되는 값이었다. CPU 느리게 하기는 메인 스레드에만 걸리고, GPU와 워커는 PC 성능 그대로다.
- **고친 방법:** 측정 결과의 스크린샷을 직접 보고 원인(`maplibre-gl.css`의 `position: relative`)을 찾았다. 흉내 측정의 한계를 문서에 적고, 판단은 로딩 시간과 실제 폰 측정에 근거했다. 실제 저사양 폰 FPS는 베타 전에 따로 잰다.

### 기기 시계 보정
- **잘한 것:** 별도 서버 함수를 만들기 전에 Vercel CDN의 캐시 응답(HIT)도 `Date` 헤더가 현재 시각인지 먼저 확인했다. 덕분에 HEAD 요청 한 번으로 보정해서, 이브 밤 트래픽에도 서버 함수를 부르지 않는다. 테스트 13개를 먼저 쓰고 구현했다. 실제 브라우저에서 `Date.now()`를 10분 늦게, 7분 빠르게 바꿔 서울 카운트다운이 진짜 시각과 맞는 것을 확인했다. 같은 조건에서 보정 전 코드는 각각 10분, 7분 틀렸다.
- **틀린 것:** MapLibre 확정 PR을 올릴 때, 검사를 반복문으로 돌리면서 실패해도 멈추지 않게 짜서 `typecheck` 실패 상태로 커밋과 push가 진행됐다. 원인은 시험 빌드가 남긴 `.next/types`였고 커밋 내용에는 문제가 없었지만, "커밋 전 통과 필수" 규칙을 어긴 절차였다. 기존 `useNow`에는 `speed=-60`이면 시간이 거꾸로 흐르는 버그도 있었다.
- **고친 방법:** 검사는 실패하면 멈추도록 하고, `.next`를 지운 깨끗한 상태에서 다시 확인했다. 배속은 0보다 큰 유한한 수만 받도록 고치고, 그 경우를 테스트로 고정했다.
