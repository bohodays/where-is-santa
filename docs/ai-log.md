### 경로 계산 규칙
- **잘한 것:** 산타 위치를 "시각 → 위치" 순수 함수로 정의하자는 구조를 바로 제안했다. 데모 모드와 테스트가 같은 원리로 풀렸다.
- **틀린 것:** 기획서 초안에서 AI가 도착 규칙을 "현지 시계 자정 + 시간대 안에서 경도 보정"으로 적었다. 이 방식은 중국처럼 넓은 시간대에서 경로가 앞뒤로 튄다.
- **고친 방법:** "해 기준 자정(경도 ÷ 15)" 규칙으로 바꾸고, 카슈가르(베이징 시간대, 서경 쪽)가 델리 다음에 도착하는지 테스트로 고정했다.
- **줄어든 시간:** 약 10시간 → 3시간, 7시간 줄어듦 (추정. 해 기준 자정·날짜변경선 규칙 조사, 대권 보간과 이진 탐색 구현. 남은 3시간은 규칙 검토와 초안 오류 수정)

### 첫 설치 검증과 lock 파일·CI 정리
- **잘한 것:** 처음으로 실제 npm 설치 환경에서 typecheck, lint, test(15개), build를 돌렸고 모두 통과했다. 고칠 코드는 없었다. Windows에서 만든 lock 파일이 Linux CI에서도 동작하는지 미리 확인했다. Linux용 바이너리 항목이 있는지 보고, CI의 npm 10으로 `npm ci --dry-run`을 돌렸고, `npm ci`로 새로 설치한 뒤 네 검사를 다시 돌렸다.
- **틀린 것:** 검사는 모두 통과했지만 `npm install`과 `npm audit`에서 취약점 15건(moderate 9, high 3, critical 3)이 나왔다. `next@15.2.4`는 설치할 때 보안 취약점 경고도 뜬다. 검사 통과만으로는 의존성이 안전한지 알 수 없다.
- **고친 방법:** lock 파일을 커밋하고 CI를 `npm ci`와 `cache: npm`으로 바꿨다(`chore/lockfile-npm-ci` 브랜치). 취약점은 아직 고치지 않았다. 버전을 올리는 일은 별도 변경으로 나눠 판단받기로 했다. 바꾼 CI는 PR #1에서 통과했고, 머지는 사람이 직접 했다.
- **줄어든 시간:** 약 1.5시간 → 0.5시간, 1시간 줄어듦 (추정. lock 파일과 CI 정리. Linux CI 호환성까지 미리 확인하는 시간 포함)

### 의존성 보안 업데이트
- **잘한 것:** 버전을 올린 뒤 audit을 다시 돌려 안 풀린 취약점을 찾았다. `npm install`이 의존성 충돌(ERESOLVE)로 막혔을 때 `--force` 없이 원인을 찾아 해결했다. critical은 3건에서 0건, 전체는 15건에서 8건으로 줄었다.
- **틀린 것:** AI가 audit 안내만 보고 `vitest`는 2.1.9로 해결되고 현재 메이저 안에서 끝난다고 말했다. 실제로는 critical이 그대로 남아서 5.1.0까지 메이저 업그레이드가 필요했다. `next` 15.5.29도 `postcss` 8.4.31을 고정해서 쓰므로 high가 남았다.
- **고친 방법:** `next`와 `eslint-config-next`는 15.5.29, `vitest`는 5.1.0, `@types/node`는 22.20.5로 올렸다. `vitest` 5에 맞춰 `engines.node`도 22.12 이상으로 올렸다. 앞으로 "이 버전으로 해결된다"는 말은 설치 후 audit 결과로 확인하고 한다. 남은 8건은 `postcss`(Next 15 내부와 직접 의존성)와 린트 도구 쪽이다. Next 16 전환은 기술 스택 규칙과 관련되어 사람이 판단한다.
- **줄어든 시간:** 약 3시간 → 1시간, 2시간 줄어듦 (추정. ERESOLVE 원인 찾기, vitest 메이저 업그레이드 판단)

### postcss 취약점 overrides 처리
- **잘한 것:** 빌드 전 CSS를 기준선으로 저장해 두고 변경 후 결과와 비교했다. 운영 의존성의 audit은 2건에서 0건, 전체는 8건에서 6건(moderate)으로 줄었고, CSS는 바이트 단위로 같았다.
- **틀린 것:** 첫 시도에서 `overrides`를 넣었는데도 lock 파일에 옛 `postcss` 8.4.31이 남아 실제로는 적용되지 않았다. `npm ci`와 네 검사가 모두 통과했고 CSS도 같아서, 그 결과만 봤다면 해결됐다고 오해할 뻔했다.
- **고친 방법:** audit과 `npm ls`에 남은 8.4.31을 보고 문제를 찾았다. lock 파일 전체를 다시 만들지 않고 `next`만 다시 설치해 적용했고, `next`가 실제로 불러오는 버전이 8.5.32인지 확인했다. Next 16으로 올릴 때 이 `overrides`는 지운다.
- **줄어든 시간:** 약 2시간 → 0.5시간, 1.5시간 줄어듦 (추정. overrides가 lock 파일에 적용되지 않는 문제 찾기, CSS 결과 비교)

### 시간대 경계 사례 테스트
- **잘한 것:** 30분·45분 시간대, 넓은 단일 시간대, 날짜변경선 양쪽을 테스트 24개로 고정했다. 기대값은 코드 결과를 복사하지 않고 공식으로 직접 계산했다. 일부러 넣은 버그 12개 중 기존 테스트는 5개를 잡았고, 새 테스트는 12개를 모두 잡았다. 이번 테스트로 찾은 코드 버그는 없었다.
- **틀린 것:** 기존 "밤에 도착" 테스트는 시각만 보고 날짜는 보지 않아서 하루 밀린 오류를 놓칠 수 있었다. 날짜변경선 비행도 위치가 유효한 값인지만 확인해서, 지구 반대쪽으로 도는 버그를 잡지 못했다. 처음 작성한 새 테스트도 시간대의 분을 버리는 보정 버그 1개를 놓쳤다.
- **고친 방법:** 현지 도착을 날짜까지 비교하고, 모든 구간에서 산타가 최단 경로 위에 있는지 별도 공식으로 확인했다. 놓친 버그는 일부러 버그 넣기에서 발견해 분 단위 보정 테스트를 추가했다. 이 테스트는 실제 도시에 없는 가상 조합으로 규칙만 고정한다.
- **줄어든 시간:** 약 6시간 → 1.5시간, 4.5시간 줄어듦 (추정. 30분·45분·날짜변경선 기대값을 손으로 계산, 일부러 버그 12개 넣어 보기)

### 지도 성능 시험과 MapLibre 확정
- **잘한 것:** 시험 화면에 측정 패널(LCP, 지도 준비 시간, FPS, 긴 프레임)과 결과 복사 버튼을 넣어, 폰에서 잰 값을 그대로 받아 비교했다. 카카오톡 인앱 브라우저에서도 지도가 동작하는 것을 확인했다. 저사양 흉내 측정에서는 로딩 시간(느린 4G 첫 방문 8.2초)이 핵심 문제라는 것을 찾았다.
- **틀린 것:** 지도 영역의 높이가 0이라 지도가 안 보였는데, 콘솔 오류가 없고 측정값도 정상이라 숫자만으로는 알 수 없었다. 저사양 흉내 측정의 FPS가 60으로 나온 것도 그대로 믿으면 안 되는 값이었다. CPU 느리게 하기는 메인 스레드에만 걸리고, GPU와 워커는 PC 성능 그대로다.
- **고친 방법:** 측정 결과의 스크린샷을 직접 보고 원인(`maplibre-gl.css`의 `position: relative`)을 찾았다. 흉내 측정의 한계를 문서에 적고, 판단은 로딩 시간과 실제 폰 측정에 근거했다. 실제 저사양 폰 FPS는 베타 전에 따로 잰다.
- **줄어든 시간:** 약 10시간 → 3시간, 7시간 줄어듦 (추정. 측정 패널이 있는 시험 화면, 워커 설정, 저사양 흉내 측정. 남은 3시간은 폰 측정과 결과 판단)

### 기기 시계 보정
- **잘한 것:** 별도 서버 함수를 만들기 전에 Vercel CDN의 캐시 응답(HIT)도 `Date` 헤더가 현재 시각인지 먼저 확인했다. 덕분에 HEAD 요청 한 번으로 보정해서, 이브 밤 트래픽에도 서버 함수를 부르지 않는다. 테스트 13개를 먼저 쓰고 구현했다. 실제 브라우저에서 `Date.now()`를 10분 늦게, 7분 빠르게 바꿔 서울 카운트다운이 진짜 시각과 맞는 것을 확인했다. 같은 조건에서 보정 전 코드는 각각 10분, 7분 틀렸다.
- **틀린 것:** MapLibre 확정 PR을 올릴 때, 검사를 반복문으로 돌리면서 실패해도 멈추지 않게 짜서 `typecheck` 실패 상태로 커밋과 push가 진행됐다. 원인은 시험 빌드가 남긴 `.next/types`였고 커밋 내용에는 문제가 없었지만, "커밋 전 통과 필수" 규칙을 어긴 절차였다. 기존 `useNow`에는 `speed=-60`이면 시간이 거꾸로 흐르는 버그도 있었다.
- **고친 방법:** 검사는 실패하면 멈추도록 하고, `.next`를 지운 깨끗한 상태에서 다시 확인했다. 배속은 0보다 큰 유한한 수만 받도록 고치고, 그 경우를 테스트로 고정했다.
- **줄어든 시간:** 약 5시간 → 1.5시간, 3.5시간 줄어듦 (추정. CDN Date 헤더 확인, 테스트를 먼저 쓴 구현, 시계를 틀리게 만든 브라우저 확인)

### 국내 시군구 데이터 출처 확정
- **잘한 것:** 검색 요약만 믿지 않고 공공데이터포털 원본 페이지에서 이용 조건을 확인했다. 같은 기관 자료도 페이지마다 1유형, 2유형, "제한 없음"으로 표기가 달랐기 때문이다. 경계 데이터(2025년 기준)에 없는 2026년 변경(화성 4개 구, 인천 개편)을 찾아, 행정동 경계를 묶는 방식으로 반영했다. 변환 스크립트가 행정동 배정 누락·중복을 직접 검사하게 했다. 결과 좌표는 독립 출처(GeoNames)와 비교했는데, 거리 중앙값이 1.7km였다.
- **틀린 것:** 처음 검색 요약에는 GeoNames를 쓰면 된다는 방향도 있었다. 실제 데이터를 받아 보니 이름 일부가 빠져 있고, 군위군의 소속 시도가 옛 정보이고, 일반구도 없었다. 변환 첫 실행은 mapshaper `-filter` 식이 참·거짓을 돌려주지 않아 실패했다.
- **고친 방법:** GeoNames는 세계 도시에만 쓰고, 국내는 SGIS로 정했다. 필터 식은 `!!GROUP_ID`로 고쳤다. 섬 지역 대표점(옹진군=백령도)의 한계는 `docs/data-sigungu.md`에 적었다.
- **줄어든 시간:** 약 12시간 → 2.5시간, 9.5시간 줄어듦 (추정. 공공데이터 이용 조건 비교, SHP 변환, 2026년 행정구역 변경 조사와 행정동 배정 검증. 남은 2.5시간은 데이터 받기와 결정)

### 지도 장애 대응 (A+B)
- **잘한 것:** 기획서의 대안(PMTiles 자체 호스팅) 대신, 의존성과 계정이 필요 없는 퍼블릭 도메인 윤곽 지도(gzip 28KB)로 대응하는 안을 제안했다. 장애 5가지(정상, 전체 차단, 타일만 차단, 응답 없음, 지도 JS 차단)를 실제 브라우저에서 재현해 모두 확인했다. 지도 JS를 동적 import로 나눠 첫 로드 JS가 397kB에서 108kB가 되는 것도 함께 확인했다.
- **틀린 것:** 첫 시험에서 "타일만 차단"이 실패했다. 코드 문제가 아니라, MapLibre가 타일을 워커에서 받는데 차단을 페이지에만 걸어서 타일이 그대로 받아진 것이었다. 결과 숫자만 봤다면 코드 버그로 잘못 고칠 뻔했다.
- **고친 방법:** 실패한 순간의 스크린샷을 보고 타일이 정상으로 그려진 것을 확인해, 시험 방법의 문제임을 찾았다. 워커에도 차단을 걸어 다시 시험해 통과했다. 이 함정은 `docs/spike-map-fallback.md`에 적었다.
- **줄어든 시간:** 약 6시간 → 1.5시간, 4.5시간 줄어듦 (추정. 윤곽 지도 데이터 준비, 장애 5가지 재현 시험)

## 2주차 (11월 16일 ~ 22일) — 디자인

### 시안 비교와 1안 확정

### 세계 지도 (SantaMap, MapAttribution)
- **잘한 것:** 운영 빌드를 headless Chrome으로 열어 타일 지도·낮 지도·윤곽 지도(OpenFreeMap 전체 차단, 타일만 차단, 응답 없음)·지도 없음을 모두 재현하고, 페이지와 워커 모두에 차단을 걸었다(1주차 시험에서 배운 것). 지도를 끌면 따라가기 버튼이 나오고 누르면 산타가 가운데로 돌아오는지 마우스 입력으로 확인했다. 지도 JS가 출발 전에는 받아지지 않는지 네트워크 기록으로 확인했다.
- **틀린 것:** (1) 시험 코드의 장애 감지("스타일을 읽었는가")를 그대로 가져왔는데, 스타일을 코드 안에 두면 늘 바로 읽혀서 OpenFreeMap을 막아도 윤곽 지도로 바뀌지 않았다. (2) 1주차에 겪은 "MapLibre CSS가 지도 칸을 relative로 바꿔 높이가 0" 문제를 또 만들었다. 검사(axe, 상태 값)는 모두 통과했는데 스크린샷에는 지도가 없었다. (3) 우리 동네 표시가 들른 도시와 같은 금색이라 헷갈렸고, 따라가기 버튼이 나오면 출처와 버튼 글자가 줄바꿈됐다.
- **고친 방법:** (1) "첫 타일이 왔는가"로 감지를 바꾸고 응답 없음까지 다시 확인했다. (2) 바깥 칸이 자리를 잡고 지도 칸은 `h-full w-full`, 코드 주석에 이유를 남겼다. 숫자 검사만 믿지 않고 스크린샷을 꼭 보는 순서로 했다. (3) 우리 동네는 흰 점 + 빨간 테두리, 버튼과 출처는 위아래 두 줄로.
- **남은 일:** 실제 저사양 폰 FPS(12/14 베타 전), 느린 4G에서 10초 기준. 첫 화면 CSS에 한글 글꼴 선언(@font-face 371개, gzip 약 55 kB)이 들어 있어 첫 화면 속도에 영향이 있을 수 있다(이번 변경과 무관, 따로 살핀다).

### 도착 순서 시트 (ArrivalList, arrivalRows, 뒤로 가기로 닫기)

- **잘한 것:** 새 의존성은 이유와 대안(임시 스크립트, Cypress, Vitest 브라우저 모드)을 먼저 보이고 승인받았고, 나온 지 2주가 안 된 최신판(1.65.1) 대신 1.65.0으로 고정했다. axe는 이미 설치된 axe-core를 써서 의존성을 하나로 줄였다. 지금까지 임시 스크립트로 하던 확인 중 핵심을 저장소의 E2E 7개로 옮기고 CI에 넣었다. 기기 시계만 바꾸면 앱이 서버 Date 헤더로 되돌린다는 점을 미리 짚어, 서버 HEAD 응답도 같은 가짜 시각으로 맞추는 `fixTime`을 만들었다. 3번 반복해 21/21로 흔들림이 없는지 보고, `<head>` 데모 스크립트를 일부러 빼서 테스트가 실제로 실패하는지도 확인했다.
- **틀린 것:** (1) 준비 스크립트(CLS·속성 기록)를 오류 수집 fixture 안에 넣었는데, 그 fixture를 쓰지 않는 장면에는 걸리지 않았다. (2) 동네 결과 버튼 이름을 "서울 마포구"로 짐작했는데 실제로는 "마포구 서울 · …"였다. (3) 헤드리스 브라우저의 그래픽 드라이버 알림(GPU stall)을 앱 오류로 셌다. (4) 헤드리스로만 돌려 보고 끝냈다. 사람이 `--headed`로 돌리자 3개가 실패했다. 창 있는 브라우저만 `/favicon.ico`를 요청하는데 앱에 아이콘이 없어 404가 났다(실제 사용자도 같다).
- **고친 방법:** fixture를 `auto: true`로 바꿔 모든 장면에 걸리게 했고, 버튼 이름은 화면 코드를 읽고 맞췄다. 드라이버 알림은 `[.WebGL-`로 시작하는 것만 따로 빼고 이유를 주석에 적었다(다른 경고는 그대로 실패). favicon 404는 테스트에서 빼지 않고 앱 아이콘을 만들어 고치기로 했다(공유 카드 작업과 함께).
- **줄어든 시간:** 약 1일 → 3시간, 5시간 줄어듦 (추정)

### 공유 카드 (SharePanel, OG 이미지, 앱 아이콘)
- **잘한 것:** 시안대로 남은 시간을 미리보기 그림에 넣기 전에, 메신저가 그림을 오래 저장해 금방 틀린다는 점을 짚었다. 도착 시각·인사말 위치·아이콘을 먼저 물어 정했다. 그 덕에 그림을 동네별로 빌드 때 만들 수 있어 이브 밤 서버 부담이 없고, Next 내장 `next/og`로 새 의존성이 없다. 서버 그림과 화면 미리보기가 같은 컴포넌트(`ShareCardArt`)를 써서 둘이 어긋나지 않는다. 시트를 닫자마자 다른 시트를 열면 방문 기록 칸이 엇갈린다는 것을 코드로 먼저 확인하고, 시트 안에서 내용만 바꾸게 설계했다. E2E 11/11, `--headed`도 11/11, Storybook 16장면 × 4모드 axe 0. 320×568·큰 글씨에서 위치를 재서 시트가 버튼을 덮는 것을 찾아 고쳤다. 첫 화면 JS +2 kB.
- **틀린 것:** (1) 파일에 쓴 유니코드 이스케이프(백슬래시 u2028 등)가 실제 보이지 않는 문자로 들어가 정규식이 깨졌다. (2) 기본 인사말을 21자로 잘못 셌다(실제 22자, 시안의 "19 / 40자"도 틀린 값). (3) 마포구 id를 kr-11440으로 짐작했다(실제 kr-11140). (4) 응답 검사(404)가 favicon도 잡는다고 주석에 썼는데, 아이콘을 빼 보니 favicon 요청은 페이지의 응답 이벤트에 오지 않았다(콘솔 검사가 잡았다). (5) 서버를 멈출 때 npx만 멈추고 node가 3100번 포트에 남아 있었다.
- **고친 방법:** (1) 이스케이프를 스크립트로 다시 써 넣고 테스트로 확인했다. (2) 기대값을 22로 고쳤다(새로 쓴 테스트라 바뀐 기존 기대값은 없다). (3) 데이터에서 id를 찾아 썼다. (4) 주석을 사실대로 고치고, favicon은 share.spec의 `<link rel=icon>`·`/icon.svg` 200 검사가 맡게 했다. (5) 포트를 쓰는 프로세스를 찾아 멈추고 다시 띄웠다.
