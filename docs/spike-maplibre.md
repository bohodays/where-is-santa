# 지도 성능 시험 (MapLibre + OpenFreeMap)

`spike/maplibre` 브랜치 전용. 결과를 보고 지도 라이브러리를 확정한 뒤, 시험 코드는 지운다.

- 시험 화면: `/spike/map` (`src/components/spike/MapSpike.tsx`)
- 기획서 목표: 모바일 LCP 2.5초 이내, 저사양 폰에서 산타 이동 60fps
- `maplibre-gl` 6.16.0 (2026-10-25 배포, BSD-3-Clause). 최신 6.17.0은 나온 지 이틀이라 쓰지 않았다.

## 측정 방법

1. PR 미리보기 주소에서 아래 주소를 폰으로 연다. Vercel 로그인 화면이 나오면 로그인한다.
2. 지도가 뜨고 **15초 이상** 기다린다. FPS는 지도 준비 2초 뒤부터 잰다.
3. **결과 복사**를 눌러 아래 표나 PR 댓글에 붙여 넣는다.
4. 같은 주소를 **새로고침해서 한 번 더** 잰다. 첫 방문(캐시 없음)과 재방문을 비교한다.

| 기호 | 바꾸는 것 | 주소 뒤에 붙일 값 |
|---|---|---|
| A | 기본 (positron, DOM 마커) | `/spike/map?demo=2026-12-25T00:20:00%2B09:00&speed=60` |
| B | 지도 레이어 마커 | A + `&marker=layer` |
| C | 카메라가 산타를 따라감 | A + `&follow=1` |
| D | 무거운 스타일 | A + `&style=liberty` |
| E | 빠른 배속 (부하 시험) | `speed=60`을 `speed=600`으로 |

가능하면 폰 두 대로 잰다: 쓰고 있는 폰, 그리고 오래된 폰(가족 폰 등). 저사양 폰이 없으면 PC Chrome 개발자 도구의 성능 탭에서 CPU를 6배 느리게 하고 잰다.

## 측정값 읽는 법

| 값 | 뜻 | 목표 |
|---|---|---|
| LCP | 화면의 가장 큰 글자·이미지가 보인 시각. 지도(canvas)는 LCP 대상이 아니라 측정값 패널이 잡힌다 | 2.5초 이내 |
| 지도 load / idle | 지도 스타일을 읽은 시각 / 첫 화면 타일을 다 그린 시각. **실제 "지도가 보이는" 시각은 idle** | 3초 이내(설계 원칙 "3초 안에 산타") |
| FPS 평균·최저 | 산타가 움직이는 동안 초당 프레임 | 평균 55 이상, 최저 30 이상 |
| 긴 프레임 | 50ms 넘게 걸린 프레임 수. 많으면 끊겨 보인다 | 0에 가깝게 |

## 실험실 측정 (2026-11-09, PC에서 Lighthouse 13.5.0, 모바일 흉내: CPU 4배 느리게, 느린 4G)

| 화면 | 성능 점수 | LCP | TBT | 전송량 |
|---|---|---|---|---|
| `/` 지금 메인 화면 | 99 | 1.8초 | 100ms | 114KiB |
| `/spike/map` A (3회) | 61~63 | 3.5~3.6초 | 1.8~2.5초 | 1,363KiB |

- 메인 스레드에서 MapLibre 코드 실행에 약 2.7초가 걸렸다(CPU 4배 느리게). TBT가 큰 이유다.
- 전송량 중 지도 타일·스프라이트·글꼴이 약 850KiB다.
- Next 빌드 기준 `/spike/map` 첫 로드 JS는 397kB(메인 106kB). 그와 별도로 워커 파일이 519KB(압축 전)다.
- 헤드리스 Chrome은 WebGL을 소프트웨어로 그려서 **FPS는 여기서 잴 수 없다.** 폰 측정이 필요하다.
- 실험실 값은 흉내 낸 값이라 실제 폰과 다를 수 있다. 판단은 폰 측정으로 한다.

## 시험하며 알게 된 것

1. **워커 주소:** MapLibre 6은 워커 주소를 `import.meta.url`로 찾는데, webpack을 거치면 이 값이 `file://`이 되어 못 찾는다. 빌드 전에 워커를 `public/maplibre/`로 복사하고 `setWorkerUrl`로 알려준다(`scripts/copy-maplibre-worker.mjs`).
2. **지도 영역 크기:** `maplibre-gl.css`가 지도 영역을 `position: relative`로 덮어써서 `absolute inset-0`이 무시되고 높이가 0이 됐다. 콘솔 오류도 없고 측정값도 정상이라, 화면을 직접 보고서야 알았다.
3. **북극:** 메르카토르 지도는 극지방을 그리지 못해서, 출발 전 "북극에서 대기"를 지도에 그대로 찍을 수 없다. 시험에서는 북위 85도로 잘랐다. 디자인에서 표현 방법을 정해야 한다.
4. **보간용 시각:** 지금 `useNow`는 1초마다 값만 준다. 프레임마다 보간하려면 배속(데모 속도)도 알아야 해서, 시험 코드는 URL을 다시 읽었다. 시계 보정 작업 때 `useNow`가 보간에 필요한 값을 같이 내주도록 바꾼다.
5. **첫 화면:** 지도 JS가 무거워 메인 스레드를 오래 잡는다. 본 구현에서는 카운트다운 글자를 먼저 보여주고 지도는 그 뒤에 불러오는 방식을 검토한다.

## 판단 기준 (측정 후 결정)

- **MapLibre 유지:** 저사양 폰에서 A 또는 B가 FPS 평균 55 이상이고, 지도 idle이 3초 안팎이다.
- **조정 후 유지:** FPS는 괜찮고 첫 로딩만 느리다. 글자를 먼저 보여주고 지도를 나중에 불러오기, 가벼운 스타일, 타일 줌 제한 등으로 해결한다.
- **대안 검토:** 저사양 폰에서 FPS 최저가 30 미만이거나 끊김이 심하다. Leaflet + 래스터 타일, 또는 단순한 자체 벡터 지도(SVG/Canvas)를 시험한다.
